# CatVision v1 接口规范（契约冻结版）

> 权威定义：`contracts/v1/*.schema.json`。
> Python 绑定：`contracts/python/catvision_contracts/models.py`。
> 两份必须逐字段一致——`pytest tests/contract` 会强制检查，不一致 CI 直接红。

**冻结日期：2026-10-22。** 冻结的意思是：从今天起改字段要开 `contract:` PR 并两个模块 approve，
不是「不能改」，是「不能悄悄改」。

---

## 0. 一页看懂

```
        摄像头与联调                猫脸识别                  耳标识别            决策层
  ┌──────────────────┐      ┌──────────────────┐   ┌──────────────────┐   ┌──────────────┐
  │  摄像头 / 视频源  │─────▶│  猫脸 + 个体识别  │──▶│   剪耳 / 绝育     │──▶│  投票 + 决策  │
  └──────────────────┘      └──────────────────┘   └──────────────────┘   └──────────────┘
        FramePacket                CatFace[]              EarNotch[]          DetectionEvent
                                                                                    │
                                                                            ActionEvent（投粮/TNR）
```

| 契约 | 谁产出 | 谁消费 | 关键约束 |
|---|---|---|---|
| `FramePacket` | 摄像头模块 | 猫脸模块、耳标模块 | 只给 `image_path`，不塞 base64 |
| `CatFace` | 猫脸模块 | 耳标模块、决策层 | **7 个关键点必须齐全**（耳尖可为 null） |
| `EarNotch` | 耳标模块 | 决策层 | **`visible=false` ⇒ `notched=null`** |
| `DetectionEvent` | 决策层 | 前端 | 聚合投票后对外，单帧结果不对外 |
| `ActionEvent` | 决策层 | 执行器 / 前端 | 投粮 / TNR / 告警 |

## 1. 通用约定

| 项 | 约定 |
|---|---|
| 版本字段 | 每个契约都有 `schema` 常量，如 `"catvision.frame_packet/1.0"`。它是判别字段，**必填** |
| 多余字段 | 所有对象 `additionalProperties: false`。写错字段名会报错，不会静默忽略 |
| 时间 | 一律 ISO-8601 **带时区**（`...Z` 或 `+08:00`）。禁止裸本地时间 |
| 坐标 | 像素坐标 `[x, y]`，相对 `packet.width/height`；`bbox` 一律 `[x, y, w, h]`（左上角 + 宽高） |
| 左右 | **一律指猫的左右，不是画面的左右。** 猫正对镜头时，它的左耳在画面右侧 |
| 概率 | `similarity` / `confidence` / `score` / `det_score` 都在 `[0, 1]` |
| ID | `cat_id` 稳定且全局唯一（`cat-001`）；`track_id` 只需在一段视频内稳定（`t-0001`） |
| 图片 | 不进 JSON。`FramePacket.image_path` 给路径，下游自己读 |

## 2. FramePacket —— 摄像头模块 → 猫脸模块 / 耳标模块

```json
{
  "schema": "catvision.frame_packet/1.0",
  "packet_id": "cam0-20261022T101500.123-000042",
  "camera_id": "cam0",
  "captured_at": "2026-10-22T10:15:00.123Z",
  "seq": 42,
  "width": 640,
  "height": 480,
  "format": "jpeg",
  "image_path": "/dev/shm/catvision/frames/cam0/f000042.jpg",
  "image_sha1": "a1b2c3…",
  "source": { "kind": "csi", "uri": "csi://0" }
}
```

| 字段 | 必填 | 说明 |
|---|---|---|
| `packet_id` | ✓ | 全局唯一。下游所有结果都要带回来，用于追溯是哪一帧 |
| `camera_id` | ✓ | 多点位部署时区分摄像头 |
| `captured_at` | ✓ | 带时区 |
| `seq` | ✓ | 从 0 递增，丢帧一眼能看出来 |
| `width` / `height` | ✓ | 坐标系的基准，**不是**原始分辨率 |
| `format` | ✓ | `jpeg` / `png` |
| `image_path` | ✓ | 本机可读路径。Pi 上在 `/dev/shm`（内存盘） |
| `image_sha1` | | 图片内容哈希，用于去重/校验 |
| `source.kind` | ✓ | `csi` / `usb` / `rtsp` / `file` / `synthetic` |

**为什么只给路径：** 进程间不搬 1MB 的图，Pi4 只有 1GB 内存。
跨机/跨语言直接读文件，不用为 base64 再抄一遍编码。

## 3. CatFace —— 猫脸模块 → 耳标模块 / 决策层

```json
{
  "schema": "catvision.cat_face/1.0",
  "packet_id": "cam0-…-000042",
  "track_id": "t-0001",
  "bbox": [180.0, 160.0, 120.0, 140.0],
  "det_score": 0.93,
  "landmarks": {
    "left_eye": [200.0, 220.0],
    "right_eye": [280.0, 220.0],
    "nose": [240.0, 260.0],
    "left_ear_base": [195.0, 180.0],
    "right_ear_base": [285.0, 180.0],
    "left_ear_tip": [180.0, 150.0],
    "right_ear_tip": null
  },
  "head_pose": { "yaw": 3.0, "pitch": -1.0, "roll": 0.5 },
  "identity": {
    "cat_id": "cat-001",
    "name": "大橘",
    "similarity": 0.88,
    "decision": "matched",
    "gallery_version": "g-2026w42"
  },
  "quality": { "blur": 120.0, "brightness": 140.0, "is_usable": true }
}
```

### 3.1 `landmarks` 是猫脸和耳标模块之间的唯一接口

7 个点全部在 `required` 里（键必须存在）。值可以是 `null`（表示看不见），但不能缺键。
耳标模块完全依赖 `*_ear_base` 和 `*_ear_tip` 裁耳部 ROI。

> 耳尖不可见时**给 `null`，不要瞎填坐标**。填错比缺省更糟：耳标模块会拿错 ROI 去判剪耳。

### 3.2 `identity.decision` 三态

| 值 | 含义 | 下游行为 |
|---|---|---|
| `matched` | 认定是档案里的某只猫 | `similarity ≥ 0.80` 才可能投粮 |
| `unknown` | 档里没这只猫 | 不投粮；可考虑建档 |
| `ambiguous` | 像好几只，说不准 | 不投粮；调高阈值再确认 |

> **宁可 `unknown`，不要乱 `matched`。** 误投粮 = 给错的猫吃，还让真正该吃的猫饿着。

### 3.3 `quality`

`is_usable=false` 的帧不参与投票（聚合层直接跳过）。这样猫脸模块可以放心输出不自信的结果，
由质量标记而不是瞎猜来兜底。

## 4. EarNotch —— 耳标模块 → 决策层

```json
{
  "schema": "catvision.ear_notch/1.0",
  "packet_id": "cam0-…-000042",
  "track_id": "t-0001",
  "left":  { "visible": true,  "notched": true,  "score": 0.91, "bbox": [180, 150, 40, 40] },
  "right": { "visible": false, "notched": null,  "score": null, "bbox": null },
  "neutered": { "value": true, "source": "ear_notch", "confidence": 0.91, "rule": "any_ear_notched" },
  "model_version": "earnotch-v0.1"
}
```

### 4.1 硬规则：`visible=false` ⇒ `notched=null` 且 `score=null`

这条同时在三处强制：

1. JSON Schema 的 `allOf/if-then`
2. pydantic 的 `model_validator`
3. `pytest tests/contract` 里的断言

看不见就说看不见。理由是不对称的：把已绝育判成未绝育只是让志愿者白跑；
把未绝育判成已绝育，这只猫永远不会进 TNR 名单。

### 4.2 `neutered` 是**规则合成的结论**，不是模型的直接输出

`rule` 四选一：`any_ear_notched`（默认，TNR 通行做法）、`both_ears_notched`、
`left_only`、`right_only`。用 `EarNotch.from_ears(...)` 生成，规则放配置里，不写死在模型里。

## 5. DetectionEvent —— 决策层 → 前端

单帧结果**不对外**。决策层按 `(camera_id, track_id)` 累积投票，猫离开画面后发一条：

```json
{
  "schema": "catvision.detection_event/1.0",
  "event_id": "det-3f2a1b…",
  "emitted_at": "2026-10-22T10:15:12.000Z",
  "camera_id": "cam0",
  "track_id": "t-0001",
  "cat": { "cat_id": "cat-001", "name": "大橘", "similarity": 0.88, "decision": "matched" },
  "neutered": { "value": true, "confidence": 0.91 },
  "votes": { "identity": { "cat-001": 8 }, "ear": { "neutered": 8 } },
  "evidence": {
    "frames_seen": 8,
    "concurrent_tracks": 1,
    "first_seen": "2026-10-22T10:15:02.000Z",
    "last_seen": "2026-10-22T10:15:12.000Z",
    "best_frame_path": "/dev/shm/catvision/frames/cam0/f000045.jpg",
    "snapshot_url": null
  }
}
```

| 字段 | 为什么存在 |
|---|---|
| `votes` | 出问题时能回答「为什么判成这只猫」。调试和前端展示都用得上 |
| `evidence.frames_seen` | 只看到 1 帧就投粮，和稳定看 20 帧，可信度完全不同 |
| `evidence.concurrent_tracks` | **多猫同框时不投粮**。这是防止一只猫吃光的关键 |
| `evidence.best_frame_path` | 前端出图 / 志愿者看现场 |
| `evidence.snapshot_url` | 前端填，后端不生成 |

聚合规则（`pipeline/aggregate.py`）：
- `identity` 得票率 ≥ `0.60` 才 `matched`，否则 `ambiguous`
- `ear` 票数取多数；完全平手 → `value=null`（不下结论）

## 6. ActionEvent —— 决策层 → 执行器 / 前端

| `type` | 触发条件 | 备注 |
|---|---|---|
| `FEED_DISPENSE` | `matched` + `similarity ≥ 0.80` + 单猫 + 距上次 > 6h | 原型阶段 `payload.dry_run=true` |
| `TNR_TASK_CREATED` | `neutered.value=false` + `confidence ≥ 0.80` | 后续推给志愿者 |
| `ALERT` | 异常（画面全黑、模型加载失败…） | 预留 |

```json
{
  "schema": "catvision.action_event/1.0",
  "event_id": "act-9c1d…",
  "emitted_at": "2026-10-22T10:15:12.100Z",
  "type": "FEED_DISPENSE",
  "track_id": "t-0001",
  "cat_id": "cat-001",
  "reason": "识别到已建档猫 cat-001，similarity=0.88",
  "payload": { "cat_id": "cat-001", "portion_g": 30, "dry_run": true, "device": "dry-run" },
  "status": "queued"
}
```

`status`：`queued` → `executed` / `failed` / `skipped`。

> **dry-run 的语义**：事件照常入队（`status=queued`），执行端看到 `payload.dry_run=true` 就不开电机。
> 这样 6 小时冷却能正常写库，dry-run 期间才测得出「反复投粮」的问题。

## 7. 改契约的流程

1. 改 `contracts/v1/*.schema.json`
2. 同步改 `contracts/python/catvision_contracts/models.py`
3. 更新 `contracts/CHANGELOG.md`（CI 会检查这一条）
4. `pytest tests/contract -q`
5. 开 PR，标题带 `contract:`，其余两个模块 approve
6. 破坏性变更 → 新建 `contracts/v2/`，v1 保留到三个模块都不再用它

**新增字段算不算破坏性？** 只要对方可能没实现读它，就算。宁可加 v2。
